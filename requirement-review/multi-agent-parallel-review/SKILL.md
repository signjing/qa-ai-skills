# 多Agent并行需求评审

## 任务目标
- 本Skill用于:需求文档的多维度并行评审，提升评审效率
- 能力包含:完整性审查、一致性审查、可测试性审查
- 触发条件:用户提供需求文档、PRD或技术方案，并要求"并行评审"、"多维度评审"或"需求评审"

## 评审架构

```
主Agent（汇总者）
├── 子Agent-1: 完整性审查
│   ├── 产品经理视角
│   ├── 测试工程师视角
│   ├── 后端工程师视角
│   ├── 前端工程师视角
│   └── 业务运营视角
├── 子Agent-2: 一致性审查
│   ├── 产品经理视角
│   ├── 测试工程师视角
│   ├── 后端工程师视角
│   ├── 前端工程师视角
│   └── 业务运营视角
└── 子Agent-3: 可测试性审查
    ├── 产品经理视角
    ├── 测试工程师视角
    ├── 后端工程师视角
    ├── 前端工程师视角
    └── 业务运营视角
```

## 评审角色定义

详见 [references/roles.md](references/roles.md)

5个评审角色：
- **产品经理**: 业务价值、用户故事、验收标准
- **测试工程师**: 测试覆盖、边界条件、异常场景
- **后端工程师**: 接口设计、数据模型、技术可行性
- **前端工程师**: 交互设计、页面还原、用户体验
- **业务运营**: 业务场景、运营规则、数据分析

## 操作步骤

### 步骤一：接收需求文档

接收用户提供的需求文档内容，确认为待评审对象。

### 步骤二：并行启动3个子Agent评审

同时启动3个子Agent，各自执行评审：

**子Agent-1: 完整性审查**
- 按角色串行审查：产品经理 → 测试工程师 → 后端工程师 → 前端工程师 → 业务运营
- 输出: 完整性评审报告

**子Agent-2: 一致性审查**
- 按角色串行审查：产品经理 → 测试工程师 → 后端工程师 → 前端工程师 → 业务运营
- 输出: 一致性评审报告

**子Agent-3: 可测试性审查**
- 按角色串行审查：产品经理 → 测试工程师 → 后端工程师 → 前端工程师 → 业务运营
- 输出: 可测试性评审报告

### 步骤三：汇总评审结果

主Agent整合3份子报告，生成综合评审报告：

```markdown
# 需求评审综合报告

## 评审概要
- 评审维度: 完整性 | 一致性 | 可测试性
- 评审角色: 5个（产品经理、测试工程师、后端工程师、前端工程师、业务运营）
- 整体评级: [通过/有条件通过/需修改]

## 完整性审查结果
### 通过项
- ...

### 需修改项
- ...

### 建议项
- ...

## 一致性审查结果
### 通过项
- ...

### 需修改项
- ...

### 建议项
- ...

## 可测试性审查结果
### 通过项
- ...

### 需修改项
- ...

### 建议项
- ...

## 综合结论
- 严重程度汇总: Critical[N] High[N] Medium[N] Low[N]
- 下一步行动: [进入开发/返回修改/重新评审]
```

## 使用示例

### 示例1: 完整评审流程
- 场景/输入:用户提供完整的PRD文档
- 预期产出:综合评审报告
- 关键要点:文档需包含功能描述、业务流程、验收标准

### 示例2: 快速评审
- 场景/输入:用户说"帮我快速评审下这个需求"
- 预期产出:简化版评审报告（3个维度的核心问题）
- 关键要点:适用于时间紧张的轻量级评审

### 示例3: 重点评审
- 场景/输入:用户说"重点关注可测试性"
- 预期产出:可测试性详细报告 + 其他维度摘要
- 关键要点:适用于测试阶段的针对性评审

## 注意事项
- 子Agent之间完全独立，可并行执行
- 每个子Agent内部按角色串行执行，确保视角完整性
- Critical级别问题必须全部修复才能通过评审
- 汇总时需平衡3个维度的权重，避免单一维度主导结论
